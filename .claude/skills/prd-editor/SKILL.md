# PRD Editor

프로젝트 루트의 `PRD_*.md` 문서를 작성/수정하는 전문 스킬입니다.

> 이 스킬은 사용자와 대화하며 **분석 → 설명 → 승인 → 적용** 흐름을 따릅니다.
> 승인 루프가 필수이므로 반드시 메인 대화 안에서 실행합니다(서브에이전트로 위임 금지).

## 대상 문서 찾기

1. 프로젝트 루트에서 `PRD_*.md` 패턴으로 파일을 탐색한다.
2. 파일이 없으면 → **신규 작성 모드**. 사용자에게 제목(프로젝트명)을 확인한 뒤 `PRD_{제목}ver1.md` 형식으로 새로 만든다.
3. 파일이 1개 있으면 → 그 파일을 수정 대상으로 한다.
4. 파일이 여러 개(버전이 여러 개) 있으면 → 파일명의 `verN` 숫자가 가장 큰 파일을 최신 버전으로 간주하고, 사용자에게 "가장 최근 버전인 `{파일명}`을 수정하는 것이 맞는지" 확인한다.

## Workflow

PRD 변경/작성 요청 시 반드시 아래 4단계를 순서대로 수행합니다. **어떤 단계도 생략하지 마세요.**

### Phase 1: Codebase & Context Analysis (코드베이스/문맥 분석)

요청이 프로젝트의 실제 상태에 비추어 타당한지 검토합니다.

1. **관련 자료 탐색**
   - 대상 PRD 문서 전체를 읽는다.
   - `docs/refactoring/TECHSPEC.md`가 있으면 함께 읽어 이미 확정된 기술 설계와 충돌하는지 확인한다.
   - 요청과 관련된 실제 코드(`src/` 등)를 Glob/Grep/Read로 확인하여, "이미 구현된 기능"을 요구사항으로 다시 추가하려는 것은 아닌지, 반대로 "이미 구현되지 않은 것으로 문서화된 기능"이 실제로는 구현되어 있어 문서가 낡은 것은 아닌지 확인한다.

2. **타당성 평가 기준**
   - 요청된 변경이 기존 PRD의 목적/비전(개요 및 목적 section)과 부합하는가?
   - 기존 PRD의 **Out of Scope** 섹션에 이미 명시적으로 제외된 항목과 모순되지 않는가? (모순되면 사용자가 스코프를 되돌리려는 의도인지 확인 필요)
   - 실제 코드베이스 구현 상태와 모순되지 않는가?
   - 이미 확정된 TECHSPEC(있는 경우)의 아키텍처 전제와 충돌하지 않는가?

3. **분석 결과 기록**
   ```
   [분석 대상]: 어떤 PRD/TECHSPEC/코드 파일을 확인했는지
   [현재 상태]: PRD 문서의 현재 내용 요약 + 코드베이스 구현 상태
   [요청 내용]: 사용자가 요청한 변경
   [타당성]: 타당함 / 부분적으로 타당함 / 타당하지 않음
   [근거]: 판단의 근거
   ```

### Phase 2: Conflict Check (충돌 검사)

1. **충돌 검사 항목**
   - **기존 PRD 내용과의 중복/모순**: 같은 요구사항이 이미 다른 절에 다르게 기술되어 있지 않은지
   - **Out of Scope 충돌**: 새 요구사항이 기존에 범위 밖으로 명시된 항목을 다시 범위 안으로 끌어오는 것은 아닌지
   - **TECHSPEC 정합성**: `docs/refactoring/TECHSPEC.md`가 존재한다면, 이미 그 문서가 전제한 아키텍처/스택과 신규 요구사항이 충돌하지 않는지 (충돌 시 TECHSPEC도 함께 갱신이 필요함을 안내)
   - **버전/마일스톤 일관성**: 마일스톤 표, 성공 지표 표, 최종 승인 표 등 문서 내 다른 표와 신규 내용이 모순되지 않는지

2. **충돌 발견 시**
   - 충돌 내용을 명확히 기술
   - 해결 방안 제시 (기존 내용 수정, 새 내용 조정, 병합, 또는 TECHSPEC 갱신 필요 여부 안내)

### Phase 3: Explain to User (사용자에게 설명)

분석 결과를 사용자에게 **반드시** 설명합니다. 생략 금지.

**설명 포맷:**

```markdown
## PRD 변경 분석 결과

### 1. 코드베이스/문맥 분석

- **확인한 문서/파일**: [PRD 파일명, TECHSPEC 유무, 확인한 코드 경로]
- **현재 상태**: [요약]
- **타당성**: [타당함/부분적/타당하지 않음] - [이유]

### 2. 충돌 검사

- **기존 PRD 충돌**: 없음 / [중복 또는 모순 내용]
- **Out of Scope 충돌**: 없음 / [충돌 내용]
- **TECHSPEC 정합성**: 없음(TECHSPEC 없음 또는 문제 없음) / [충돌 내용, TECHSPEC 갱신 필요 여부]

### 3. 권장 사항

[변경을 진행할지, 수정이 필요한지, 대안이 있는지, 버전을 올려야 하는지 등]
```

### Phase 4: Get User Feedback (사용자 피드백 수집)

**필수**: 변경 적용 전에 반드시 1개 이상의 질문으로 사용자 피드백을 받습니다.

1. **질문 유형 예시**
   - "분석 결과를 검토하셨습니까? 이대로 진행해도 될까요?"
   - "이 변경으로 버전을 {현재}.0 → {현재}.1로 올릴까요, 새 파일(`ver{N+1}`)로 분리할까요?"
   - "Out of Scope였던 [항목]을 다시 범위 안으로 가져오는 것이 맞습니까?"
   - "이 요구사항 변경이 이미 작성된 TECHSPEC과 충돌하는데, TECHSPEC도 함께 갱신할까요?"

2. **피드백 확인 후에만 변경 적용**
   - 사용자가 명시적으로 승인한 경우에만 PRD 문서 수정
   - 사용자가 수정을 요청하면 Phase 1로 돌아가 재분석

## Document Writing Rules

PRD 문서 작성/수정 시 준수할 규칙:

1. **한글로 작성**: PRD 문서는 반드시 한글로 작성
2. **Clean Document**: 변경 흔적을 본문에 남기지 않음 ("추가됨", "변경됨", "~~삭제~~" 금지). 문서는 항상 처음부터 그렇게 작성된 것처럼 깔끔하게 유지. 변경 이력은 본문이 아니라 Change Log 파일에만 남긴다.
3. **중복 제거**: 새 내용이 기존 내용과 중복되면 단순 추가가 아닌 통합/수정/제거로 문서를 탄탄하게 유지
4. **문서 구조 유지**: 기존 PRD의 표준 구조(개요/목적, 문제 정의, 목표 및 성공 지표, 사용자 여정, 기능 요구사항, 비기능 요구사항, 기술 스택, 마일스톤, Out of Scope, 리스크, 확인 필요 항목)를 최대한 유지하고, 새 절이 필요할 때만 추가
5. **버전/날짜 갱신**: 실질적인 내용 변경 시 문서 상단의 `버전`, 하단의 `마지막 업데이트` 날짜, "최종 승인" 표를 함께 갱신한다. 사소한 오타 수정은 버전을 올리지 않는다.
6. **확인 필요 항목 관리**: 사용자가 "확인 필요 항목(Open Questions)"에 답을 주면 해당 항목을 절에서 제거하고 본문의 확정된 내용으로 반영한다. 임의로 답을 지어내지 않는다.

## Change Log

수정 완료 후, PRD 파일과 같은 폴더에 `PRD_preference.md` 파일에 변경 로그를 추가합니다.

- 개요는 **한글로 한 줄** 요약하며, 날짜(`[YYYY-MM-DD]`)와 변경 이유/배경을 함께 기록
- 파일이 없으면 새로 생성
- 기존 로그는 유지하고 **맨 아래에 새 항목 추가**
- 사소한 오타 수정이나 포맷팅 변경은 기록하지 않아도 됨

**형식 예시:**

```markdown
- [2026-07-16] 데이터 컬럼명 확정("데이터1/2/3" → 실제 명칭) 반영 - Open Questions 해소
- [2026-07-20] Post-MVP 고도화 계획에 "가계부 연동" 절 추가 - 사용자 신규 요구사항
```

## Important Files

| File                              | Purpose                                    |
| ---------------------------------- | ------------------------------------------- |
| `PRD_*.md`                         | 제품 요구사항 문서 (수정 대상)              |
| `PRD_preference.md`                | 변경 로그 파일 (PRD와 같은 폴더)            |
| `docs/refactoring/TECHSPEC.md`     | 기술 설계 문서, 정합성 확인용               |
| `.claude/CLAUDE.md`                | 프로젝트 개요 및 아키텍처 참조              |
| `package.json`                     | 실제 스택/의존성 확인용                     |

## Anti-Patterns (하지 말아야 할 것)

- ❌ 분석 없이 바로 수정
- ❌ 사용자 확인/승인 없이 변경 적용
- ❌ 충돌 검사 생략 (특히 Out of Scope, TECHSPEC 정합성)
- ❌ 한글이 아닌 언어로 PRD 작성
- ❌ 변경 로그 누락
- ❌ 확인 필요 항목의 답을 임의로 지어내서 채우기
- ❌ 실제 코드베이스 구현 상태와 모순되는 내용을 검증 없이 추가
